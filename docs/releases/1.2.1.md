# KH PTZ Control 1.2.1

Status: prepared release candidate. Target Raspberry Pi acceptance is pending.
This document does not certify physical camera behavior or approve deployment.

## Changes since 1.2.0

- Camera recall and connection handling, stable control-panel behavior during
  transport loss, and offline VISCA/Qt regression checks.
- Session and background-work lifetime guards, including keeping cameras on
  when that close option is selected.
- ATEM link-state reporting, reconnection, stale-event rejection and connection
  attempt retirement. Commands are not automatically replayed on reconnection.
- Installation/readiness checks, GUI-session quiescence before code replacement,
  recovery error reporting, and backup/restore validation.
- State-file writes and evidence redaction fixes. See CHANGELOG.md for details.

## Known limits

- PyATEMMax 1.0b9 lacks the PiP API used by the application. Production PiP is
  unsupported through that path. No upstream keyer is selected or written by
  guessing. Confirm the M/E, upstream keyer and exclusive PiP use, then review
  and physically validate any implementation separately.
- Automatic ATEM discovery and TCP Scan are unavailable. Enter the switcher IP
  manually and use Reconnect ATEM plus monitor status. Advisory diagnostics
  marked not_run are not evidence that a switcher is down.
- Automated loopback, Qt and systemd-command harnesses are not target hardware
  tests. Successful software commands do not prove physical motion or stopping.
- Installer manager discovery/stop/verification is not an atomic exclusion
  against a concurrent new login or manual GUI start. Do not start a GUI while
  replacing code. The user GUI is reopened manually after the update.

## Target-Pi acceptance

With the operator present and outside a live event:

1. Confirm backup, rollback route, installed identity and target package hash.
2. Check upgrade with system and user GUI paths, including a lingering user
   manager, logout/login and reboot. Confirm a single current-code GUI and no
   stale process across replacement. Do not change linger policy implicitly.
3. Check initial consent, both-camera start, presets and delayed recalls,
   joystick release/STOP, camera switching, zoom, focus and exposure on the
   physical 800x480 touchscreen.
4. Check a controlled network cut and recovery. The panel must keep its place,
   motion must be disabled while unavailable, and no stale movement may replay.
5. Check close choices (keep cameras on versus power off), session end and app
   restart. Verify camera outcomes, not just the UI state.
6. Check ATEM program/preview and deliberate CUT/AUTO outside live use, link
   loss/recovery and no command replay. PiP remains unsupported unless a
   separately reviewed and accepted implementation has passed hardware checks.
7. Run the installed offline self-test and a 3-4 hour physical soak using
   docs/SOAK_TEST.md; review logs. Investigate unexpected errors before release.

No operator window is booked by this document. Hardware testing requires the
operator's confirmed presence and an approved, reviewed candidate.

## Packaging and rollback

Build only from the final reviewed commit. Include installable source with
Git identity when the installer requires it; a plain GitHub source archive is
not automatically equivalent to the verified install package. Record contents,
version, commit, checksums and dependency inventory. Verify extraction in an
isolated directory without running a privileged installation.

The existing v1.2.0 tag and release are immutable. A 1.2.1 candidate must never
replace their bytes or redirect their tag. Publish v1.2.1 only for the exact
accepted commit; if changes follow validation, rebuild and repeat affected gates.

Record the previous installed ref and whether data restoration is needed.
A code rollback alone is not a promise to undo runtime data changes. Use a
verified pre-update backup and an explicit supported restore route.
