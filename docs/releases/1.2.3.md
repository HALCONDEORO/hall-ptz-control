# KH PTZ Control 1.2.3

Status: prepared release candidate for operator testing, not a stable release.
Prepared on 2026-11-14. Physical target-Pi acceptance remains pending.
This document does not authorize an installation or certify camera behavior.

## Changes since 1.2.2

- Serialize concurrent source-YAML camera configuration saves with the existing
  per-path transaction lock, so two simultaneous saves can no longer lose one
  camera's change. Adds a `config.yaml.lock` sidecar only in the writable
  source configuration directory; `/etc` permissions and the runtime-overlay
  branch are unchanged (#323).
- Let the newest pending preset per camera supersede earlier still-pending
  preset requests. A recall already in flight always completes; intermediate
  queued presets for that camera are skipped instead of all being visited in
  FIFO order. STOP, session boundaries, other event types and per-camera
  independence are unchanged (#324).
- Mark the zoom percentage as unconfirmed - dimmed value, `ZOOM ?` caption and
  an explicit tooltip - from the moment the post-settle inquiry starts until a
  current camera read confirms it. A failed or silent read keeps the mark; no
  polling, retry or timeout was added (#325).

All changes already integrated in v1.2.2 are retained. The v1.2.1 and v1.2.2
tags and published assets must remain unchanged; this candidate has its own
version identity.

## Known limits and exclusions

- Only not-yet-started presets are superseded. A preset recall already in
  flight is never interrupted, cancelled or replaced mechanically; it completes
  or fails normally. Superseded entries remain lightweight queue entries until
  drained; this is not a bounded-queue feature.
- The unconfirmed zoom mark is a display state, not a new camera reading. A
  failed inquiry still cannot establish the actual zoom position.
- At 800x700 the pre-existing fixed-layout viewport crops the right panel, so
  the unconfirmed indicator is not verified at that window size; no
  small-screen-layout improvement is claimed.
- Source-YAML serialization covers `patch_runtime_config` callers only. Direct
  calls to `config.writer.patch_config_yaml` outside that wrapper are unchanged.
- Physical camera movement, interruption, stopping, touchscreen behavior and
  target-Pi installation/rollback are still pending operator validation.
- Existing ATEM/PiP and installation limits in `1.2.1.md` and `1.2.2.md`
  continue to apply.

## Pre-update and acceptance checks

1. Establish the real installed ref, launch path and GUI mode. A version label
   alone does not prove the source commit or installation layout.
2. Close the app cleanly and retain verified installation/configuration/data
   backups off the Pi before changing anything. The installer does not create a
   pre-update backup automatically. A data ZIP is not a complete SD-card image.
3. Verify the exact reviewed release commit, package contents and SHA-256. Keep
   the previous known-good installation and its supported recovery route.
4. With the operator present and outside live use, test both camera selections,
   preset calls while another recall is still moving (only the latest pending
   preset should follow the in-flight one), successful and failed zoom
   adjustments (the dimmed `ZOOM ?` state must clear on a real reading), and
   concurrent camera-configuration saves. Compare the actual lens state with
   the displayed ring and percentage.
5. Repeat the relevant physical checks and soak described in `1.2.1.md` and
   `../SOAK_TEST.md`. Software regression checks are not hardware acceptance.
